Pub-sub message queue

A Kafka-style message queue in miniature: publishers append to a topic's log, and consumer groups read from it at their own pace by offset. Every group sees every message; within a group each message is handled once.

Low-level designConcurrency

Picture it. A newsroom noticeboard where every notice gets a number. The sports desk and the politics desk each keep a bookmark of the last number they've read. Within the sports desk, whoever is free takes the next notice and moves the bookmark on.

Requirements

Functional

  • Create topics; publish messages to a topic and get back their offset.
  • Consumer groups: each group receives every message; consumers in one group share the work.
  • Consumers block (with a timeout) when they have caught up.
  • A group can seek back to replay older messages.

Non-functional

  • Publishing from many threads at once gives each message a unique, increasing offset.
  • Within a group, no message is processed twice and none is skipped.
  • Slow groups don't slow down publishers or other groups.

Entities and relationships

  • The log is the source of truth. Publishing appends; reading never deletes. Retention (by age or size) trims the oldest part later.
  • Offsets are positions in the log. A group's committed offset is the next message it will process, so replay is just seek(older offset).
  • Scaling: real brokers split a topic into partitions, each its own log, and assign each partition to one consumer in a group. Ordering is then guaranteed per partition (per key), not across the topic.

Design patterns used

  • Publish–subscribe: publishers don't know who consumes; groups subscribe independently.
  • Observer (pull-based): consumers pull at their own pace instead of being pushed to, which gives natural back-pressure.
  • Event sourcing: the append-only log can rebuild any downstream state by replaying it.

How a request flows

Delivery guarantees depend on when the offset moves. Advancing it before processing gives at-most-once (a crash loses the message); advancing it after processing gives at-least-once (a crash means it's processed again, so handlers should be idempotent). This design advances on hand-out, which is at-most-once per group.

Concurrency

  • publish appends and assigns the offset under the topic lock, so offsets are unique and gap-free even with many publishers.
  • Readers wait on a Condition with a timeout; signalAll wakes every group waiting on that topic.
  • Each group has its own lock, so claiming the next offset is atomic within a group and independent of other groups.
  • Lock order is always group → topic, never the reverse, so there's no deadlock.

Code

Three consumers in one group share ten messages and each is handled exactly once; another group reads everything in order and replays from an offset; four publisher threads append 100 messages with no duplicate offsets.

Shown in Java and Python: JavaScript runs your code on one thread, so locks and conditions have no real equivalent there. Java and Python show the design with real threads.

Common mistakes

  • Deleting a message once one consumer reads it, which breaks independent groups and replay.
  • Busy-polling in a while (true) loop instead of waiting on a condition.
  • Assuming global ordering across partitions or consumers.
  • Non-idempotent handlers with at-least-once delivery.

Interview follow-ups

  • Add partitions and assign them to the consumers in a group; rebalance when one leaves.
  • Commit offsets only after processing; persist them so restarts resume.
  • Dead-letter queue for messages that keep failing.
  • Push-based delivery with per-subscriber queues and back-pressure.
