Parking lot

The most common LLD warm-up: spots of different sizes, vehicles that fit some of them, tickets, fees, and several entry gates that must never hand out the same spot twice.

Low-level designConcurrency

Picture it. A multi-storey car park where four barrier gates open at once at 9 a.m. Each barrier must grab a free bay for its driver, and two drivers must never be sent to the same bay.

Requirements

Functional

  • Spots are SMALL, MEDIUM or LARGE; motorcycles fit any spot, cars fit medium or large, trucks need large.
  • Park a vehicle: pick the smallest free spot that fits and issue a ticket.
  • Leave: free the spot and charge a fee based on vehicle type and time parked.
  • Reject a vehicle that is already inside, and report free spots per type.

Non-functional

  • Several gates park and release vehicles at the same time.
  • A spot is never assigned twice; a released spot becomes available immediately.
  • Fee rules can change without touching the lot (Strategy).

Entities and relationships

  • VehicleType and SpotType are enums ordered by size, so "fits" is just spot.ordinal() >= vehicle.ordinal().
  • ParkingLot is the single entry point; gates (or a REST controller) call it. Real systems add Level and Floor objects, but they don't change the core logic: free spots per type, and an index of active tickets.
  • FeePolicy is injected. Hourly, flat weekend and free-for-the-first-15-minutes pricing are new classes, not edits.

Design patterns used

  • Strategy: FeePolicy for pricing; a spot-selection strategy (nearest to the gate, fill one level first) is the usual follow-up.
  • Singleton (sometimes requested): one ParkingLot per process. Inject it rather than reaching for a global.
  • Factory: build spots and levels from a layout description.

How a request flows

Leaving reverses it: remove the ticket from active (atomic, so a ticket can't be paid twice), compute the fee, push the spot back onto its free deque, and remove the plate.

Concurrency

  • ConcurrentLinkedDeque.pollFirst() is atomic, so two gates can never receive the same spot, with no global lock.
  • The plate set (ConcurrentHashMap.newKeySet()) rejects a second entry for the same vehicle atomically.
  • active.remove(ticketId) returns the ticket to exactly one caller, so double exits fail cleanly.
  • If a vehicle claims its plate but finds no spot, it must un-claim the plate before returning, or it can never enter again.
  • With a single lock around the whole lot the design is simpler and still correct; per-type deques simply let gates proceed in parallel.

Cost of each operation

OperationTimeWhy
parkO(number of spot types)Try each fitting size once; each poll is O(1).
leaveO(1)Hash removal plus a deque push.
free count per typeO(n) / O(1)ConcurrentLinkedDeque.size() walks the list; keep an AtomicInteger per type if you need it often.

Shown in Java and Python: JavaScript runs your code on one thread, so locks and conditions have no real equivalent there. Java and Python show the design with real threads.

Common mistakes

  • Checking isFree() on a spot and then marking it taken in a separate step: two gates both see it free.
  • Inheritance like class Car extends Vehicle with fit logic scattered in subclasses, when an enum ordering is enough.
  • Putting payment, display boards and spot allocation in one class.
  • Using floating-point money; use integer cents.

Interview follow-ups

  • Nearest-spot-to-the-entrance allocation (one heap per gate or per level).
  • Electric charging spots and reservations.
  • A display board per floor that updates as spots change (Observer).
  • Multiple lots behind one API, and what changes when the state lives in a database.
