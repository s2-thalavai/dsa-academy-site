Thread-safe LRU cache

An LRU cache keeps the most recently used entries and evicts the oldest when full. Making it thread-safe is subtle: even get changes the recency order, so a read lock is not enough. This page compares one lock, lock striping, and stopping a cache stampede.

Low-level designConcurrency

Picture it. A small shelf of the books people asked for most recently, by a busy library desk. Every time someone borrows from the shelf, that book moves to the front, so even "just looking" rearranges the shelf, and two librarians can't rearrange it at the same moment.

Requirements

Functional

  • get(key) returns the value or null and marks the key as recently used.
  • put(key, value) inserts or updates, evicting the least recently used entry when over capacity.
  • getOrLoad(key, loader) loads a missing value once, even when many threads ask together.

Non-functional

  • O(1) per operation.
  • Correct under concurrent access; size never exceeds capacity.
  • Scales with cores: hot keys shouldn't serialise every request.

Entities and relationships

  • Data structure: hash map + doubly linked list ordered by recency (see Data structure design for the hand-built version). Java's LinkedHashMap with accessOrder = true and removeEldestEntry is exactly that; Python's OrderedDict with move_to_end is the same idea.
  • Why not a read-write lock? get moves the entry to the front of the list, which is a write. Under a read lock, two gets would corrupt the list.
  • Lock striping: segment = hash(key) mod N. Each segment is an independent LRU with capacity total / N. Eviction becomes approximately LRU (per segment), which is almost always acceptable.

Design patterns used

  • Decorator / wrapper: LockedLRU wraps a non-thread-safe map and adds locking around every call.
  • Lock striping: N locks over N partitions, the trick behind early ConcurrentHashMap.
  • Single flight (request coalescing): the first thread to miss a key loads it; the others wait on its future instead of all hitting the database.

How a request flows

After winning the right to load, the thread checks the cache once more: a previous loader may have finished between this thread's miss and its claim. Without that second check, an unlucky thread loads the value twice.

Concurrency

  • One ReentrantLock per cache (or per segment) guards both the map and the recency list together, since they must change as one.
  • Never call the loader while holding the cache lock: a slow database call would block every other key.
  • In-flight loads live in a ConcurrentHashMap<K, CompletableFuture<V>>; putIfAbsent decides atomically who loads.
  • Remove the in-flight entry in finally, and complete the future exceptionally on failure so waiters don't hang.
  • Production caches (Caffeine) avoid a global lock by recording reads in a buffer and replaying them onto the LRU list in batches.

Code

The concurrent parts print invariants that hold on every run: the size after 16,000 random operations, and how many times the loader ran when 8 threads missed the same key together.

Shown in Java and Python: JavaScript runs your code on one thread, so locks and conditions have no real equivalent there. Java and Python show the design with real threads.

Common mistakes

  • Using a read lock for get even though it reorders the list.
  • Synchronising get and put separately but doing if (get(k) == null) put(k, load(k)) outside: a check-then-act race that loads twice.
  • Holding the cache lock during the slow load.
  • Leaving a failed load in the in-flight map, so every later request waits forever.
  • Using ConcurrentHashMap alone and believing it gives LRU order.

Interview follow-ups

  • Add a time-to-live per entry; how do you expire entries nobody reads again?
  • Switch the eviction policy to LFU without changing callers (Strategy).
  • Report hit rate and eviction counts without adding contention (LongAdder).
  • Make the cache distributed (consistent hashing across nodes).
