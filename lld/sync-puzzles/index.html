Synchronisation puzzles

LeetCode's concurrency problems are small puzzles about ordering threads. Each one has a standard tool: semaphores for turn-taking, a barrier for grouping, a condition for "wait until it's my number", ordered locks against deadlock, and a work queue with a counter for parallel search.

Low-level designConcurrency

Picture it. A relay race: a runner can't start until the baton is in their hand. A semaphore is the baton: whoever finishes their leg hands it to exactly the runner who goes next.

Requirements

Functional

  • Print in Order: first, second, third run in that order whatever order the threads start.
  • FooBar / Zero-Even-Odd: two or three threads alternate output.
  • Building H2O: group threads into molecules of two H and one O.
  • Fizz Buzz Multithreaded: four threads each print their kind of number in sequence.
  • Dining Philosophers: five threads share five forks without deadlock.
  • Web Crawler Multithreaded: crawl every page on one host in parallel, each exactly once.

Non-functional

  • Correct on every run, whatever the scheduler does.
  • No busy-waiting and no deadlock.

Entities and relationships

Puzzle Tool Idea
Print in Order semaphores at 0 first releases second's semaphore; second releases third's.
FooBar, Zero-Even-Odd a semaphore per turn each thread acquires its own and releases the next thread's.
Building H2O semaphores + barrier the semaphores admit 2 H and 1 O; the barrier waits for all three.
Fizz Buzz lock + condition each thread waits until the current number is its kind, prints, advances, signals all.
Dining Philosophers lock ordering always pick up the lower-numbered fork first, so no cycle can form.
Web Crawler pool + concurrent set visited.add(url) decides who crawls a page; a pending counter detects the end.

Design patterns used

  • Baton passing: a semaphore released by one thread and acquired by exactly the next is a turn token.
  • Resource ordering: the standard way to make circular wait, and so deadlock, impossible.
  • Fork–join with termination counting: the crawler finishes when the number of pending pages drops to zero.

How a request flows

Dining philosophers, why ordering works: deadlock needs a cycle where each philosopher holds one fork and waits for the next. If everyone picks up the lower-numbered fork first, philosopher 4 (forks 4 and 0) reaches for fork 0 first, the same fork philosopher 0 wants first, so the cycle can't close.

Concurrency

  • A semaphore's permits aren't tied to a thread: any thread may release, which is exactly what turn-passing needs.
  • With a condition, always signalAll when waiters wait for different predicates (fizz vs buzz), and loop on the predicate.
  • CyclicBarrier resets after each group of 3, so it can be reused for every molecule.
  • The crawler increments pending before submitting a page and decrements after its links are queued, so it can't hit zero early.

Cost of each operation

OperationTimeWhy
Turn-taking puzzlesO(n)Each step is one acquire and one release.
Dining philosophersO(meals)Each meal takes two locks.
Web crawlerO(pages + links)Each page is fetched once; parallelism hides fetch latency.

Code

Every line is the same on every run, because the synchronisation, not the scheduler, decides the order. H2O prints each molecule's atoms sorted, since the three atoms in one molecule may print in any order.

Shown in Java and Python: JavaScript runs your code on one thread, so locks and conditions have no real equivalent there. Java and Python show the design with real threads.

Common mistakes

  • Thread.sleep to "make the order right": it only makes the bug rarer.
  • Spinning on a volatile flag instead of blocking, which burns a core.
  • Using signal with one condition and several kinds of waiters: the wrong one wakes and everyone sleeps.
  • Taking forks in left-then-right order for everyone, which deadlocks when all pick up their left fork at once.
  • Ending the crawl when the queue is momentarily empty, while workers are still adding links.

Interview follow-ups

  • Solve Dining Philosophers with a waiter (a semaphore of 4) instead of ordering.
  • Make the crawler respect a per-host rate limit (see Rate limiter).
  • Solve Print in Order with CountDownLatch or CompletableFuture instead of semaphores.
  • Traffic Light Controlled Intersection: which tool fits?
