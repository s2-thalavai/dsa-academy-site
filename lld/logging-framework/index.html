Logging framework

Design a small Log4j or Python logging: named loggers with levels, a chain of handlers each with its own threshold, pluggable formatters (plain text, JSON) and sinks (console, file, pager). It shows Chain of Responsibility, Strategy and a registry working together.

Low-level design

Picture it. A newsroom's incoming wire. Every story passes along a line of desks: the website desk takes anything of general interest, the archive keeps everything, and the night editor's phone only rings for breaking news. Each desk decides for itself, then passes the story on.

Requirements

Functional

  • Levels DEBUG < INFO < WARN < ERROR; each named logger has its own minimum level, changeable at runtime.
  • A message that passes the logger goes through a chain of handlers; each handler writes it if it meets that handler's level.
  • Handlers format with a formatter (plain or JSON) and write to a sink.
  • getLogger(name) returns the same logger every time.

Non-functional

  • Cheap when disabled: a filtered-out debug call does no formatting.
  • New formats and destinations without touching the logger.
  • Safe to call from many threads.

Entities and relationships

  • Two filters: the logger's level stops a record before it's even created (so debug calls in production cost almost nothing); each handler's level then decides which sinks get it.
  • The chain is console (INFO+) → file (DEBUG+) → pager (ERROR+). This variant passes every record all the way down. The classic Chain of Responsibility stops at the first handler that handles a request, which suits approvals and middleware; logging usually wants every interested handler.
  • Formatter and Sink are strategies: PlainFormatter, JsonFormatter; MemorySink here, a file or network sink in real life.

Design patterns used

  • Chain of Responsibility: handlers linked with next; each decides whether to act, then forwards.
  • Strategy: formatters and sinks plug into handlers.
  • Registry / Singleton-per-name: getLogger(name) caches one logger per name.

How a request flows

Concurrency: the records are immutable and the chain doesn't change after set-up, so only the sinks need protecting: each sink's write is synchronised (or hands lines to a single writer thread, as in the async logger on the Snowflake IDs page).

Cost of each operation

OperationTimeWhy
Filtered-out callO(1)One level comparison; no record, no formatting.
Accepted callO(handlers)Each handler checks its level and maybe formats and writes.
getLoggerO(1)A map lookup.

Code

Time is a counter that ticks once per record that passes its logger, so a dropped call never uses a tick.

Common mistakes

  • Building the message string before checking the level (log.debug("x=" + expensive())). Check first, or pass a supplier.
  • One logger class per destination instead of separating loggers, handlers, formatters and sinks.
  • Creating a new logger on every call instead of caching by name.
  • Hand-building JSON without escaping quotes and backslashes in the message.

Interview follow-ups

  • Hierarchical loggers: app.db inherits its level and handlers from app unless set.
  • Asynchronous sinks with a bounded queue and a drop policy.
  • Rotate files by size and date; ship logs to a remote collector.
  • Add structured fields (request id, user id) through a context map.
