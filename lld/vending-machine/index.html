Vending machine

The textbook use of the State pattern. A vending machine reacts to the same buttons differently depending on its mode: with no money, "select" asks for coins; with money, it dispenses; when empty, it refuses everything. One class per mode keeps those rules apart.

Low-level design

Picture it. A ticket barrier. Tap a card when it's closed and it opens; walk through when it's open and it closes; when it's switched off for maintenance, every action just gets an "out of service" light.

Requirements

Functional

  • Accept coins of 5, 10, 25 and 100 cents; return anything else.
  • Select an item by code: dispense it if paid for, give change, refuse if sold out or underpaid.
  • Cancel returns the balance.
  • When every slot is empty the machine goes out of service; restocking brings it back.

Non-functional

  • Adding a mode (maintenance, card payment) means adding a class, not editing if chains in every method.
  • Money is in integer cents.

Entities and relationships

State transitions

State insert(coin) select(code) cancel()
Idle add to balance → HasMoney "insert money first" nothing to refund
HasMoney add to balance dispense + change → Idle (or OutOfService if all empty); or refuse and stay refund → Idle
OutOfService return the coin refuse nothing to refund

restock moves OutOfService back to Idle. Each state is stateless itself, so a single shared instance of each is enough.

Design patterns used

  • State: each mode is a class; the machine's behaviour changes by swapping its state field.
  • Singleton (per state): states hold no data, so one instance of each is shared.
  • Greedy change-making: with coin values 100/25/10/5, taking the largest coin first gives the fewest coins.

Common mistakes

  • One big switch (state) inside every method, so each new mode touches every method.
  • Forgetting to reset the balance after dispensing, so the next customer gets free credit.
  • Changing state before the action succeeds (moving to Idle when the item was sold out).
  • Greedy change with arbitrary coin systems (e.g. 1, 3, 4) can be wrong; then it's the Coin Change DP.

Interview follow-ups

  • Track the machine's own coin inventory and refuse sales it can't give change for.
  • Card payments: a PaymentProcessing state with success and failure transitions.
  • Maintenance mode entered by an operator key.
  • Concurrent use from a mobile app and the keypad: what needs locking?
