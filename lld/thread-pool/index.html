Thread pool and scheduler

A thread pool keeps a fixed set of worker threads and feeds them tasks from a queue, so you don't pay for a new thread per task or run out of memory under load. A scheduler adds tasks that run after a delay or on a period.

Low-level designConcurrency

Picture it. A taxi rank with three cabs and a queue of passengers. Cabs don't get built per passenger; they take the next person in line, drop them off and come back. A dispatcher with a diary handles the bookings for later.

Requirements

Functional

  • submit(task) returns a future for the result.
  • A fixed number of workers; tasks wait in a bounded queue.
  • shutdown() stops accepting tasks and lets queued ones finish; awaitTermination() waits for the workers.
  • schedule(task, delay) and scheduleAtFixedRate(task, delay, period), with cancellation.

Non-functional

  • A failing task must not kill its worker.
  • Back-pressure when the queue is full, instead of unbounded memory.
  • No lost tasks: anything accepted before shutdown runs.

Entities and relationships

  • Worker loop: take() a task, run it inside try/catch, repeat. The exception is kept in the task's future, so the caller sees it in get() and the worker carries on.
  • Future: FutureTask wraps a Callable, runs it once, stores the result or exception, and wakes anyone blocked in get().
  • Shutdown with poison pills: after setting the flag, put one sentinel task per worker. Each worker exits when it takes one, after finishing everything queued ahead of it.
  • Scheduler: a min-heap keyed by run time. The thread sleeps until the earliest job is due, or until a new earlier job arrives (signal).

Design patterns used

  • Command: a task is an object (Runnable/Callable) that can be queued and run later by someone else.
  • Producer–consumer: callers produce tasks, workers consume them through a blocking queue.
  • Future / promise: a placeholder for a result that isn't ready yet.

How a request flows

Sizing: CPU-bound work wants about one thread per core. I/O-bound work can use more: roughly cores × (1 + wait time / compute time).

When the queue is full, ThreadPoolExecutor offers rejection policies: abort (throw), caller-runs (the submitting thread runs it, which slows the producer down), discard, or discard-oldest. This pool blocks the caller, which is the caller-waits policy.

Concurrency

  • submit and shutdown are synchronized together, so a task can't slip into the queue after the poison pills and never run.
  • shutdown is volatile-safe because it's only read and written under the same monitor.
  • The scheduler runs each job outside its lock, so schedule() from inside a job can't deadlock.
  • Periodic jobs are re-queued with runAt += period (fixed rate). Fixed delay would use now + period after the run.
  • In Java 21, virtual threads make thread-per-task cheap for blocking I/O, but pools are still the tool for limiting CPU-bound concurrency.

Code

The scheduled jobs are 30 ms apart, so the order is the same on every run; the periodic job cancels itself after its third run.

Shown in Java and Python: JavaScript runs your code on one thread, so locks and conditions have no real equivalent there. Java and Python show the design with real threads.

Common mistakes

  • Letting a task's exception escape the worker loop, so the pool quietly loses a thread per failure.
  • Unbounded queues (newFixedThreadPool uses one): under overload memory grows until the process dies.
  • Calling future.get() from inside a task on the same small pool, which can deadlock when every worker waits.
  • Scheduling with Thread.sleep(delay) per task instead of one thread and a heap.
  • Forgetting to shut the pool down, which keeps the JVM alive.

Interview follow-ups

  • Grow the pool from a core size to a max size when the queue is full (how ThreadPoolExecutor does it).
  • Work stealing: give each worker its own deque (ForkJoinPool).
  • Add task priorities.
  • Make shutdownNow() interrupt running tasks and return the queued ones.
