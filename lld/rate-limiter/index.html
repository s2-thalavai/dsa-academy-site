Rate limiter

A rate limiter decides, for each request, whether the caller has used up their allowance. The two algorithms worth knowing by heart are the token bucket (smooth rate, allows bursts) and the sliding window log (exact count in the last N milliseconds).

Low-level designConcurrency

Picture it. A ticket machine at a car park entrance that prints one ticket per second into a tray holding at most three. Arrive with a group of three and you all get in at once; the fourth person waits until the next ticket drops.

Requirements

Functional

  • tryAcquire(user) returns allowed or denied immediately.
  • Limits are per user (or per API key, per IP).
  • Support a token bucket and a sliding window, chosen by configuration.

Non-functional

  • Thread-safe: many request threads call the limiter at once.
  • O(1) or close to it per request; memory bounded per user.
  • Testable without sleeping: time comes from an injected clock.

Entities and relationships

Algorithm State per user Bursts Accuracy
Token bucket token count + last refill time yes, up to capacity smooth average rate
Leaky bucket queue + drain rate no, output is constant smooth output
Fixed window counter count + window start up to 2× at window edges cheap but coarse
Sliding window log timestamps of recent requests no exact
Sliding window counter two counters, weighted slight approximate, O(1) memory

Token bucket refill is lazy: rather than a timer adding tokens, each call adds elapsed × rate tokens, capped at the capacity, then spends one.

Design patterns used

  • Strategy: RateLimiter is an interface; the registry is built with a factory for whichever algorithm is configured.
  • Registry with lazy creation: computeIfAbsent creates each user's limiter exactly once, even when two requests for a new user arrive together.
  • Dependency injection: the clock is passed in, so tests step time forward instead of sleeping.

How a request flows

In a real service a denied request gets HTTP 429 Too Many Requests, often with a Retry-After header computed from the time until the next token.

Concurrency

  • Each limiter's tryAcquire is synchronized: refill-then-spend is a check-then-act sequence and must be atomic.
  • Per-user locks mean one hot user can't slow everyone else down.
  • ConcurrentHashMap.computeIfAbsent guarantees one limiter per user; a plain get followed by put can create two and lose requests' state.
  • A lock-free token bucket is possible: pack tokens and timestamp into an AtomicLong and retry with compare-and-set.
  • Across many servers, keep the state in Redis and update it atomically with a Lua script (or INCR + EXPIRE for fixed windows).

Common mistakes

  • Refilling with a background thread per user. Lazy refill on each call needs no threads.
  • Reading the clock outside the lock, so two threads compute refills from different times out of order.
  • Using wall-clock time (currentTimeMillis) that can jump backwards; prefer a monotonic clock (nanoTime).
  • Never evicting idle users from the registry, so memory grows with every IP ever seen.

Interview follow-ups

  • Make the limiter work across a cluster of API servers.
  • Support different limits per plan (free, pro) and per endpoint.
  • Return how long the caller should wait before retrying.
  • Evict limiters for users idle longer than the window.
