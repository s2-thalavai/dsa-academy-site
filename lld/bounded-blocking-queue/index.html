Bounded blocking queue

A queue with a fixed capacity where put waits while it's full and take waits while it's empty. It is the heart of every producer–consumer system, thread pool and log pipeline, and the classic test of whether you can use a lock with conditions correctly.

Low-level designConcurrency

Picture it. A conveyor belt between a bakery and the packing team that holds three trays. If the belt is full the bakers stop and wait; if it's empty the packers wait. Nobody busy-waits and no tray falls off the end.

Requirements

Functional

  • put(x) adds to the tail, blocking while the queue is full.
  • take() removes from the head, blocking while it's empty.
  • offer(x, timeout) and poll(timeout) give up after a time limit.
  • size() reports how many items are waiting.

Non-functional

  • Safe with any number of producers and consumers.
  • No busy-waiting: blocked threads use no CPU.
  • FIFO order, and never more items than the capacity.

Entities and relationships

  • Circular array: head is the next item to take, tail the next free slot, and both wrap with % capacity. No shifting, so both ends are O(1).
  • One lock, two conditions: producers wait on notFull, consumers on notEmpty. A put signals notEmpty, a take signals notFull, so each wake-up goes to a thread that can now make progress.
  • Shutdown: blocking queues have no "close" by default. The usual trick is a poison pill: one sentinel item per consumer that tells it to stop.

Design patterns used

  • Producer–consumer: decouples the speed of the producers from the speed of the consumers; the queue absorbs bursts and applies back-pressure when full.
  • Monitor: the lock plus its conditions form a monitor: all state changes happen while holding the lock.

How a request flows

After a wake-up the producer re-checks count == capacity in a while loop. Another producer may have filled the freed slot first, and conditions can also wake spuriously.

Concurrency

  • Every read and write of head, tail and count happens under the lock, so updates are atomic and visible to other threads.
  • await() releases the lock atomically while sleeping and re-acquires it before returning.
  • Use signal() (one waiter) when any waiter can make progress, and signalAll() when waiters wait for different things on one condition. With two separate conditions, signal() is enough.
  • Timed waits use awaitNanos, which returns the time left; loop until it reaches zero.
  • Throughput upgrade: LinkedBlockingQueue uses two locks (one for each end), so a producer and a consumer never block each other.

Code

Two producers push 1 to 100 through a queue of capacity 3 while three consumers drain it. The totals and the capacity check come out the same on every run.

Shown in Java and Python: JavaScript runs your code on one thread, so locks and conditions have no real equivalent there. Java and Python show the design with real threads.

Common mistakes

  • if (count == capacity) await() instead of while. A second producer can overfill the queue.
  • Calling wait()/await() without holding the lock (IllegalMonitorStateException).
  • Using one condition with signal(): a producer can wake another producer, and everyone ends up asleep.
  • Forgetting to unlock in finally.
  • Stopping consumers by interrupting them mid-item, rather than with a poison pill or a shutdown flag.

Interview follow-ups

  • Make put and take not block each other (two locks, an atomic count).
  • Add drainTo(collection, max) for batch consumers.
  • How would you build a delay queue, where items become available at a given time?
  • What changes for a lock-free single-producer single-consumer ring buffer?
