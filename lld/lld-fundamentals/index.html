LLD fundamentals

Low-level design interviews check whether you can turn a vague brief into classes with clear jobs, pick the right design pattern, and keep shared state correct when many threads touch it. This page is the toolkit the rest of the section uses.

Low-level design

Picture it. Designing a restaurant kitchen. Each station has one job (SRP), new dishes don't mean rebuilding the stations (open/closed), any cook can cover any station of the same kind (Liskov), and the pass between kitchen and floor is the one place where orders are handed over safely (synchronisation).

Requirements

Functional

  • Explain each SOLID principle with a short example.
  • Show the patterns that appear across this section: Strategy, Observer, Factory, Singleton, State, Chain of Responsibility.
  • Show the Java concurrency building blocks: locks, atomics, latches and executors.

Non-functional

  • Code that is easy to extend without editing tested classes.
  • Shared state that stays correct with any number of threads.

Entities and relationships

SOLID in one line each

Principle Meaning Smell it fixes
Single responsibility A class has one reason to change. A ParkingLot that also prints receipts and charges cards.
Open/closed Add behaviour by adding code, not editing it. A switch on discount type that grows with every promotion.
Liskov substitution A subtype works anywhere its parent does. A Square extends Rectangle whose setWidth breaks callers.
Interface segregation Small interfaces that clients actually need. A Machine interface forcing printers to implement fax().
Dependency inversion Depend on interfaces; inject the implementation. new MySqlRepo() inside business logic, so tests need a database.

Composition beats inheritance in almost every LLD answer: a Checkout has a Discount instead of being a PercentOffCheckout.

Design patterns used

  • Strategy: swap an algorithm at runtime (discounts, fee rules, dispatch policies). Used in parking lot, elevator and rate limiter.
  • Observer: notify subscribers when something changes (price alerts, pub-sub, booking confirmations).
  • Factory: one place decides which concrete class to build from a type name or config.
  • Singleton: exactly one instance, created lazily and safely. Use sparingly: it is global state and makes testing harder.
  • State: an object's behaviour depends on its mode (vending machine, elevator, order lifecycle).
  • Chain of Responsibility: pass a request along handlers until one deals with it (logging, approvals, middleware).

Concurrency

  • Race condition: count++ is read, add, write. Two threads can read the same value and one update is lost.
  • Visibility: without volatile, a lock or an atomic, one thread may never see another's write. Locks give both exclusion and visibility.
  • Deadlock needs four things at once: mutual exclusion, hold-and-wait, no preemption, circular wait. Break circular wait by always taking locks in the same global order.
  • Livelock and starvation: threads keep reacting without progress, or a thread never gets the lock. Fair locks and writer preference help.
  • Always while, never if, around a condition wait: wake-ups can be spurious, and another thread may have taken the item first.
  • Unlock in finally, so an exception can't leave the lock held forever.

A method for any LLD question

  1. Clarify requirements (5 minutes): what the system must do, the scale, and which operations happen concurrently.
  2. List the nouns as candidate classes and the verbs as methods. Drop anything that is only data.
  3. Draw the class diagram: has-a (composition), is-a (interface), uses (dependency).
  4. Pick patterns where they remove a switch or a hard-coded dependency.
  5. Find the shared mutable state and decide how it's protected: one lock, finer locks, atomics, or a concurrent collection.
  6. Write the core classes and a main that walks one scenario end to end.
  7. Discuss extensions: what changes if the scale grows, or a new type is added?

Common mistakes

  • Jumping into code before agreeing the requirements and the class list.
  • Making everything a Singleton. It hides dependencies and makes tests share state.
  • Inheritance for code reuse (class Car extends ParkingSpot). Prefer composition.
  • Checking a condition and then acting on it in two separate locked sections (check-then-act race).
  • Holding a lock while calling out to unknown code (listeners, I/O), which invites deadlocks and slow paths.

Interview follow-ups

  • Why is double-checked locking broken without volatile, and why does the holder idiom avoid it?
  • When would you choose ReentrantLock over synchronized? (tryLock, timeouts, fairness, several conditions.)
  • How would you test that a class is thread-safe?
  • AtomicInteger versus LongAdder under heavy contention.

In your language

Notes for Java

AtomicInteger uses compare-and-swap, with no lock. The holder idiom (Holder.INSTANCE) relies on the JVM's guarantee that class initialisation runs once, safely.

Notes for Python

The GIL does not make counter += 1 atomic: it is several bytecodes and a thread switch can land between them. The AtomicInteger class here is a lock around an int, which is how you'd write one in Python.
