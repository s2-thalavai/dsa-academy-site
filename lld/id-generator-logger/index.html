Snowflake IDs and a thread-safe logger

Two small services every backend needs. A Snowflake ID generator makes unique, roughly time-ordered 64-bit IDs on every machine with no coordination. An asynchronous logger lets many threads log without their lines interleaving or blocking on disk.

Low-level designConcurrency

Picture it. Raffle tickets printed at several booths: each ticket shows the minute, the booth number and a counter that resets every minute, so two booths can never print the same ticket. Meanwhile one clerk copies everyone's notes into the ledger, one line at a time, so no two notes get mixed up.

Requirements

Functional

  • Generate 64-bit IDs: 41 bits of milliseconds since a custom epoch, 10 bits of machine id, 12 bits of sequence.
  • IDs from one generator strictly increase; IDs from different machines never collide.
  • Detect the clock moving backwards.
  • Log from any thread; lines are whole, keep each thread's order, and the caller never waits for I/O.

Non-functional

  • Up to 4,096 IDs per millisecond per machine, with no network calls.
  • Logging never interleaves partial lines.
  • close() flushes every queued line.

Entities and relationships

Snowflake layout (most significant bit first):

Sign Timestamp Machine Sequence
1 bit (0) 41 bits: ms since epoch (~69 years) 10 bits: 1,024 machines 12 bits: 4,096 per ms

id = (ms − epoch) << 22 | machine << 12 | seq. Sorting IDs sorts by creation time, which keeps database index inserts at the end of the B-tree.

Async logger: callers format the line and put it on a queue (cheap, never touches disk). One writer thread takes lines and appends them to the sink, so writes are naturally serialised.

Design patterns used

  • Producer–consumer: logging threads produce lines, one writer consumes them.
  • Singleton (per process): one generator per machine id; two instances with the same id would collide.
  • Dependency injection: the clock is injected, so tests can freeze time or move it backwards.

How a request flows

Alternatives: UUIDv4 needs no coordination but is random (bad index locality) and 128 bits; UUIDv7 is time-ordered and is the modern standard choice; a database sequence is simple but a single point of contention.

Concurrency

  • nextId is synchronized: reading the clock, comparing with lastTs and bumping seq form one check-then-act sequence.
  • Clock going backwards (NTP adjustment) would create duplicates; refuse, or wait until the clock catches up.
  • Machine ids must be unique: assign them from config or a coordination service at start-up.
  • The logger's queue gives each line a total order; a single writer means no locking around the sink.
  • On close(), a sentinel is queued after every real line, so the writer drains everything before exiting.
  • Bound the log queue in production and decide what to do when it's full: block, drop debug lines, or count dropped lines.

Cost of each operation

OperationTimeWhy
nextIdO(1)A few bit operations; waits at most until the next millisecond.
logO(1)One queue insert; the I/O happens on the writer thread.
Throughput4,096 IDs / ms / machineLimited by the 12-bit sequence.

Code

The first IDs use a fixed clock so the numbers are exact. The concurrency checks use the real clock and print only properties: uniqueness, per-thread ordering and whole lines.

Shown in Java and Python: JavaScript runs your code on one thread, so locks and conditions have no real equivalent there. Java and Python show the design with real threads.

Common mistakes

  • Using System.currentTimeMillis() without handling it going backwards.
  • Forgetting to reset the sequence when the millisecond changes, which wastes the sequence space.
  • Logging with System.out.println from many threads and assuming lines can't interleave in every sink.
  • Losing the last log lines because the writer thread is a daemon that dies before flushing.

Interview follow-ups

  • Assign machine ids automatically when containers start and stop.
  • Make the logger rotate files by size and day.
  • Add structured logging (JSON) and a level filter (see Logging framework).
  • Compare Snowflake with UUIDv7 and database sequences.
