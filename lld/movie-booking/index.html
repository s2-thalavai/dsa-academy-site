Movie ticket booking

BookMyShow-style booking: users pick seats, the seats are held for a few minutes while they pay, then confirmed. The hard part is making sure two people can never buy the same seat, and that abandoned holds expire.

Low-level designConcurrency

Picture it. Putting clothes on hold at a shop counter. The assistant writes your name and a time on a tag; nobody else can buy them until the time runs out, and if you come back late they may already be sold.

Requirements

Functional

  • Browse shows and see which seats are available.
  • Hold one or more seats for a user, all or nothing, for a fixed time.
  • Confirm the booking after payment; a failed payment releases the seats.
  • An expired hold no longer blocks other users and can't be confirmed.

Non-functional

  • No double booking, under any number of concurrent users.
  • Holds expire without a cleanup thread being required for correctness.
  • Contention on one popular show must not slow down other shows.

Entities and relationships

  • Seat state is derived, not stored as a flag: a seat is booked if it's in the booked set, held if it has an unexpired hold, otherwise available. Expiry therefore needs no background job; a hold past its time is simply ignored (and can be cleaned up lazily).
  • All-or-nothing holds: check every requested seat first, and only then write any holds. A failure leaves nothing behind.
  • Payment is outside the lock. Only the final confirm re-checks the hold.

Design patterns used

  • State (implicit): available → held → booked, with expiry moving held back to available.
  • Optimistic confirmation: the hold is the reservation; confirm re-validates it, so a slow payment that outlives its hold fails safely.
  • Dependency injection: the clock is injected so expiry can be tested precisely.

How a request flows

In a database the same rules become a unique constraint on (show_id, seat_id) in a bookings table, plus a holds table with an expires_at column, updated with SELECT … FOR UPDATE or a conditional UPDATE … WHERE status = 'AVAILABLE' OR expires_at < now(). The row count tells you whether you won.

Concurrency

  • One lock per show: a blockbuster's rush doesn't block other shows. ConcurrentHashMap.computeIfAbsent creates each show's lock once.
  • Check-all-then-write-all inside the lock makes multi-seat holds atomic, with no partial holds.
  • Per-seat locks are possible, but a multi-seat request must then lock seats in a fixed (sorted) order to avoid deadlock.
  • Confirm compares the hold's user and expiry under the lock, so an expired hold that someone else took over can't be confirmed.

Common mistakes

  • Holding seats one at a time and leaving earlier ones held when a later one fails.
  • A status field flipped by a cleanup thread: if the thread is late, seats stay blocked.
  • Holding the lock during the payment call.
  • Confirming without re-checking that the hold is still yours and still valid.

Interview follow-ups

  • Show seat availability live to thousands of viewers (cache plus push updates).
  • Release holds early when the user closes the page.
  • Pricing tiers and coupons (Strategy).
  • Spread across many servers: what replaces the in-memory lock?
