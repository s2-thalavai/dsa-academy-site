Read-write lock and KV store

Most stores are read far more than they're written. A read-write lock lets any number of readers in together but gives a writer the store to itself. Building one by hand shows where starvation comes from and how writer preference prevents it.

Low-level designConcurrency

Picture it. A museum gallery. Any number of visitors can look at the paintings at once, but when a curator needs to rehang a wall, new visitors are held at the door, the room empties, the curator works alone, and then everyone is let back in.

Requirements

Functional

  • get, getAll(keys) for consistent multi-key reads, put, putAll for atomic multi-key writes, and update(key, fn).
  • Many concurrent readers; a writer has exclusive access.
  • tryLockRead() fails immediately rather than waiting.

Non-functional

  • Readers never see half of a multi-key write.
  • Writers are not starved by a constant stream of readers.
  • Reads proceed in parallel.

Entities and relationships

The lock's rules (all under one internal mutex):

Operation Waits while Then
lockRead a writer is writing or waiting readers++
unlockRead — readers--; wake all if it reached 0
lockWrite a writer is writing or readers > 0 writing = true (counted as waiting meanwhile)
unlockWrite — writing = false; wake all

Making readers also wait for waiting writers is the writer preference. Without it, overlapping readers can keep readers > 0 forever and a writer never runs.

Design patterns used

  • Read-write lock: separate shared and exclusive modes for read-heavy data.
  • Monitor: the lock's own state is protected by a mutex and a condition.
  • Copy-on-write (alternative): for tiny, rarely written maps, readers can use an immutable snapshot with no lock at all.

How a request flows

In production Java, use ReentrantReadWriteLock (optionally fair) or StampedLock, whose optimistic reads take no lock at all and only retry if a write happened meanwhile. Building it by hand is a common interview question because it tests conditions, invariants and starvation.

Concurrency

  • getAll holds one read lock across all keys, so it sees either all or none of a putAll.
  • update(key, fn) is a read-modify-write, so it takes the write lock; doing get then put under separate locks loses updates.
  • signalAll (not signal) on release, because readers and writers wait on the same condition for different things.
  • Writer preference can starve readers if writes never stop. A fair lock alternates batches of readers and writers.
  • A read lock is not upgradable to a write lock here: two readers upgrading at once would deadlock.

Code

Writers update keys a and b together while readers check that they're always equal; the counter shows no lost updates; and a writer gets in while four readers keep re-acquiring the lock.

Shown in Java and Python: JavaScript runs your code on one thread, so locks and conditions have no real equivalent there. Java and Python show the design with real threads.

Common mistakes

  • Using a read lock for an operation that mutates (LRU get, lazy initialisation, counters).
  • No writer preference, so writers starve under steady reads.
  • Trying to upgrade a read lock to a write lock.
  • Forgetting finally { unlock }, which leaves the reader count wrong forever.

Interview follow-ups

  • Add versions per key and a time-based get (get(key, timestamp)).
  • Implement optimistic reads like StampedLock.
  • Shard the store so writes to different shards don't block each other.
  • Add TTL expiry and a snapshot for backups without stopping writers.
