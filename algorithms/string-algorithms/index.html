String algorithms

Pattern matching finds every place a short pattern occurs in a long text. The naive method re-reads text after every mismatch; KMP, Rabin-Karp and the Z-algorithm all avoid that and run in linear time.

Technique 15 minute read

Picture it. Proofreading for a repeated word. A careless reader who finds "the th" and then sees "e" missing starts again one letter later. A careful reader notices that the "th" they just read could be the start of the next match, and carries on from there. KMP is the careful reader.

The problem with naive search

Naive search lines the pattern up at each position of the text and compares character by character. On text like aaaaaaaab with pattern aaab, each attempt matches three characters before failing, so the work is O(n × m).

KMP (Knuth–Morris–Pratt)

When a mismatch happens after matching k characters, those k characters are known: they're the first k of the pattern. The prefix table says how much of them is also a valid start of the pattern, so KMP shifts the pattern to line that part up and keeps going. The text pointer never goes back.

Rabin-Karp

Treat a string as a number in some base (say 256), modulo a large prime. Compare the hash of the pattern with the hash of each text window. Sliding the window by one is O(1): subtract the leaving character's contribution, multiply by the base, add the new character. Equal hashes might be a collision, so confirm with a direct comparison. With a good modulus collisions are rare and the expected time is O(n + m).

The Z-algorithm

Z[i] is the length of the longest substring starting at i that matches a prefix of the string. To search, compute Z for pattern + "$" + text: every position where Z[i] equals the pattern length is a match. A window [l, r] of the rightmost match found so far lets each Z value start from a known lower bound, which keeps the whole computation linear.

When to use it

Reach for it when

  • Finding all occurrences of a pattern, or checking whether one string contains another, at scale.
  • Problems about repeated structure: shortest period, repeated substring patterns, the longest prefix that's also a suffix.
  • Comparing many substrings for equality quickly (rolling hashes).

Think twice when

  • Inputs are small and the built-in indexOf/contains/find is fine; those are well optimised in practice.
  • You need many different patterns at once. Use a trie-based automaton (Aho-Corasick).

In your language

Notes for Java

  • String.indexOf uses a simple search, worst case O(n × m), but it's fast on typical text.
  • s.toCharArray() once, then index the array, avoids repeated charAt bounds checks in hot loops.

Notes for JavaScript

  • str.indexOf, includes and search are the built-ins. For Rabin-Karp keep hash values under 2⁵³ by taking the modulus at every step.

Notes for TypeScript

  • Same as JavaScript. Return number[] of all match positions to keep the functions reusable.

Notes for Python

  • str.find and in are implemented in C and are fast; write KMP when the problem is about the prefix table itself.
  • Python ints are unbounded, but take the modulus in Rabin-Karp anyway, or hashes grow and slow down.

Code

All three find the same matches. KMP prints its prefix table, Rabin-Karp uses a rolling hash with base 256, and the Z-array is printed for a short string.

Common mistakes

  • Off-by-one in the prefix table: lps[i] describes the substring ending at i, and the prefix must be proper (shorter than the whole).
  • Forgetting to confirm Rabin-Karp matches with a direct comparison, so a hash collision reports a false match.
  • Negative values from the rolling hash subtraction. Add the modulus before taking %.
