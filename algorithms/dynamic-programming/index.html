Dynamic programming

Dynamic programming solves a problem by breaking it into overlapping subproblems, solving each one once and reusing the answers. It turns many exponential brute-force searches into polynomial time.

Technique 18 minute read

Picture it. Working out 1 + 1 + 1 + 1 + 1 + 1 + 1 on paper gives 7. Add another "+ 1" and you answer 8 instantly: you remembered the 7 instead of recounting. Dynamic programming is remembering answers to smaller questions so you never redo them.

The idea in one sentence

If a brute-force recursion keeps asking the same question, store each answer the first time and look it up after that.

Five steps to any DP solution

  1. Define the state. In plain words, what does dp[i] (or dp[i][j]) mean? For climbing stairs: "the number of ways to reach step i".
  2. Write the transition. How does a state come from smaller states? The last move was 1 step or 2, so dp[i] = dp[i − 1] + dp[i − 2].
  3. Set the base cases. dp[0] = 1 (one way to stand still), dp[1] = 1.
  4. Choose an order. Every state must be computed after the states it reads. Here: i from 2 up to n.
  5. Find the answer in the table: dp[n]. Then check whether you only need the last few rows, and shrink the space.

Memoisation vs tabulation

  • Top-down (memoisation): write the natural recursion, then cache results. You only compute the states you actually reach. Easy to write; uses the call stack.
  • Bottom-up (tabulation): fill a table from the base cases up with loops. No recursion, often faster, and it's easier to see which rows can be dropped to save memory.

Both have the same time complexity. Start with whichever is easier to get right; convert if the recursion is too deep.

The main families

  • 1D: one index of progress. Stairs, house robber, decode ways, coin change (index = amount).
  • 2D grids and two strings: dp[i][j] over prefixes or grid cells. Unique paths, LCS, edit distance.
  • Knapsack: dp[i][w] = best value using the first i items with capacity w. 0/1 (each item once) or unbounded (reuse items).
  • Interval: dp[l][r] over subranges, built from shorter ranges. Burst balloons, palindrome partitioning.
  • String DP: LCS, edit distance, longest palindromic subsequence and regular-expression matching all compare prefixes of strings.

When to use it

Reach for it when

  • The question asks for a count of ways, a minimum or maximum, or whether something is possible, and the brute force tries every choice.
  • The same smaller problem comes up repeatedly in the brute force (overlapping subproblems).
  • The best answer for the whole is built from best answers for parts (optimal substructure).

Think twice when

  • A greedy rule is provably correct; it's simpler and faster.
  • The state space is too big, such as subsets of 50 items (2⁵⁰ states).
  • Subproblems don't overlap. Plain divide and conquer is enough.

In your language

Notes for Java

  • Use int[] or long[] tables. long for counts that can overflow, and take % 1_000_000_007 when the problem says so.
  • Memoised recursion can hit StackOverflowError for n around 10⁴ to 10⁵; tabulate instead.
  • Arrays.fill(dp, Integer.MAX_VALUE) for minimisation, but guard the + 1 against overflow.

Notes for JavaScript

  • new Array(n + 1).fill(0) for 1D; Array.from({ length: n + 1 }, () => new Array(m + 1).fill(0)) for 2D (not fill([])).
  • Counts beyond 2⁵³ lose precision; use BigInt or the problem's modulus.

Notes for TypeScript

  • Typed tables (number[][]) catch row/column mix-ups less than you'd hope; name indices i for the first string and j for the second consistently.

Notes for Python

  • @functools.cache gives top-down DP in one line. The recursion limit (1,000) means deep states need sys.setrecursionlimit or tabulation.
  • dp = [[0] * (m + 1) for _ in range(n + 1)] builds independent rows.
  • Python ints don't overflow, but huge numbers get slow; apply the modulus as you go.

Code

Climbing stairs and house robber are 1D with O(1) space. Coin change and knapsack fill a table over amounts or capacities. LCS and edit distance fill a 2D table over two prefixes, and LIS checks every earlier index.

Common mistakes

  • Defining the state vaguely. Write down in words exactly what dp[i] means before coding.
  • Wrong base cases, especially for empty prefixes or amount 0.
  • Filling the table in an order where a cell is read before it's computed.
  • In 0/1 knapsack with a 1D array, looping capacity upwards, which reuses an item many times. Loop downwards.
  • Forgetting the modulus on intermediate values, so they overflow before the final %.
