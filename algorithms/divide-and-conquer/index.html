Divide and conquer

Divide and conquer splits a problem into smaller independent pieces of the same kind, solves each piece (usually recursively) and combines the answers.

Technique 12 minute read

Picture it. Counting votes in a national election. Each district counts its own ballots, regions add up their districts, and the country adds up the regions. Nobody counts every ballot, and the districts work at the same time.

The three steps

  1. Divide the input into smaller pieces, usually two halves.
  2. Conquer each piece recursively. Pieces small enough are solved directly.
  3. Combine the pieces' answers into the answer for the whole.

The pieces must be independent: solving one doesn't need the other. That's what separates divide and conquer from dynamic programming, where subproblems overlap and are cached.

Analysing the recursion tree

Write the cost as a recurrence. For merge sort, T(n) = 2T(n/2) + O(n): two halves, then O(n) to merge. Draw the tree: level 0 does n work, level 1 does two pieces of n/2, level 2 four pieces of n/4. Every level costs n, and there are log₂ n levels, so the total is O(n log n).

The master theorem, in practice

For T(n) = a·T(n/b) + O(nᵈ), with a subproblems each of size n/b:

  • if a < bᵈ, the top level dominates: O(nᵈ)
  • if a = bᵈ, every level costs the same: O(nᵈ log n)
  • if a > bᵈ, the leaves dominate: O(n^(log_b a))

Merge sort has a = 2, b = 2, d = 1, so a = bᵈ and the answer is O(n log n). Binary search has a = 1, b = 2, d = 0, so a = bᵈ again: O(log n).

Worked example: counting inversions

An inversion is a pair i < j with a[i] > a[j]. Brute force checks every pair in O(n²). Merge sort counts them for free: while merging, each time you take an item from the right half, it's smaller than every item still waiting in the left half, so add the number of items left there. The total is O(n log n).

When to use it

Reach for it when

  • The problem splits into independent halves whose answers combine cheaply: sorting, counting inversions, closest pair of points.
  • Halving the input repeatedly gets you to a trivial case: binary search, fast exponentiation.
  • Pieces could be solved in parallel.

Think twice when

  • The subproblems overlap, so the same piece is solved many times. That's dynamic programming.
  • The combine step is as expensive as solving the whole problem directly.

In your language

Notes for Java

  • Arrays.copyOfRange for halves is clear but allocates; passing lo and hi indices into one array avoids the copies.
  • ForkJoinPool and RecursiveTask run divide-and-conquer pieces in parallel; parallel streams use it underneath.

Notes for JavaScript

  • slice copies; pass index ranges for speed on large arrays.
  • Recursion depth is only log₂ n for balanced splits, so stack limits rarely matter here.

Notes for TypeScript

  • Same as JavaScript. Return tuples like [sorted, inversions] to pass two results up from each half.

Notes for Python

  • Slicing a[:mid] copies, costing O(n) per level, which is fine for O(n log n) algorithms but adds memory churn. Pass indices to avoid it.
  • Function calls are relatively slow in CPython, so a recursive divide and conquer is often slower than an iterative version of the same algorithm.

Code

Counting inversions piggybacks on merge sort. Maximum subarray checks the best sum in the left half, the right half and across the middle. Fast power halves the exponent, and majority element merges candidates from both halves.

Common mistakes

  • Forgetting the base case for size 0 or 1, or splitting a size-1 problem into sizes 0 and 1 forever.
  • Splitting unevenly by accident (such as mid = lo when hi - lo == 1), which can loop or degrade to O(n²).
  • Doing O(n) work to copy subarrays in a recursion that's supposed to be O(log n), such as binary search on slices.
