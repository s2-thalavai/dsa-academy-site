Complexity analysis

Complexity analysis predicts how an algorithm's time and memory grow as the input grows. It lets you compare solutions before writing them, and it's the first thing interviewers ask about yours.

Technique 14 minute read

Picture it. Delivering invitations. Handing one to the host is constant work. Walking down a street to every house is linear. Asking every guest to greet every other guest is quadratic: double the guests and the greetings quadruple. Big-O names the shape of that growth, not the exact minutes.

What Big-O measures

Big-O describes how the number of steps grows as the input size n grows. It ignores two things on purpose:

  • Constant factors: 3n and n are both O(n). They grow the same way.
  • Smaller terms: n² + 100n + 7 is O(n²). For large n the n² swamps the rest.

So Big-O won't tell you which of two O(n) loops is faster. It tells you which algorithm still works when n goes from a thousand to a million.

Big-O, Big-Θ and Big-Ω

These three describe bounds:

  • Big-O (upper bound): grows no faster than. Linear search is O(n).
  • Big-Ω (lower bound): grows at least as fast as. Any comparison sort is Ω(n log n) in the worst case.
  • Big-Θ (tight bound): both at once. Merge sort is Θ(n log n): never better, never worse.

In everyday use (and interviews) people say "O" when they mean the tight bound. That's fine as long as you also say which case you mean: best, average or worst. Quicksort is O(n log n) on average and O(n²) in the worst case.

How to work out the complexity of code

  1. Sequential steps add: a loop of n then a loop of m is O(n + m).
  2. Nested steps multiply: a loop of n inside a loop of n is O(n²).
  3. Halving gives a logarithm: while n > 1: n = n / 2 runs about log₂ n times.
  4. Recursion: count the calls and the work per call. f(n) calling f(n − 1) once with O(1) work is O(n). Calling f(n − 1) twice is O(2ⁿ). Splitting in half twice with O(n) work to combine (merge sort) is O(n log n).
  5. Space counts too: extra arrays, hash maps and the recursion stack.

Input size tells you the target

Judges and interviewers pick limits that hint at the intended complexity. At roughly 10⁸ simple operations per second:

Input size n Feasible complexity
up to 10–12 O(n!), O(2ⁿ · n)
up to 20–25 O(2ⁿ)
up to 500 O(n³)
up to 10⁴ O(n²)
up to 10⁶ O(n log n)
up to 10⁸ O(n)
larger O(log n) or O(1)

Amortised analysis

Some operations are usually cheap and occasionally expensive. Amortised cost is the average over any long sequence. A dynamic array's append is the classic case: most appends write one slot, but every so often the array doubles and copies everything. Over n appends the copies total less than n, so the amortised cost is O(1). The code below measures it.

When to use it

Reach for it when

  • Choosing between approaches before you code: estimate each one's complexity against the input limits.
  • Explaining your solution in an interview: state time and space, and justify both.
  • Spotting a hidden cost: list.remove(0), string += in a loop, contains on a list.

Think twice when

  • Comparing two algorithms with the same Big-O for small inputs. Constants and cache behaviour decide those; measure instead.

In your language

Notes for Java

  • Know the hidden costs: ArrayList.add(0, x) and remove(0) are O(n); LinkedList.get(i) is O(n); String += in a loop is O(n²); HashMap operations are O(1) average.
  • Collections.sort and Arrays.sort on objects are O(n log n) and stable (TimSort). Arrays.sort on primitives is dual-pivot quicksort: O(n log n) average, not stable.

Notes for JavaScript

  • shift, unshift, splice in the middle and includes are O(n). push, pop and Map/Set operations are O(1) average.
  • Array.prototype.sort is O(n log n) and stable in modern engines. Without a comparator it sorts as strings: [10, 9, 1].sort() gives [1, 10, 9].

Notes for TypeScript

  • The types don't change costs. Same notes as JavaScript.

Notes for Python

  • list.insert(0, x), pop(0), x in list and slicing are O(n). dict and set lookups are O(1) average.
  • sorted and list.sort are TimSort: O(n log n), stable, and O(n) on already-sorted data.
  • Rough budget: CPython does about 10⁷ simple operations per second, so O(n²) at n = 10⁴ is borderline.

Common mistakes

  • Counting nested loops without checking their bounds. A loop inside a loop that runs a fixed 26 times is O(26n) = O(n).
  • Forgetting the cost of library calls inside a loop, such as slicing or indexOf.
  • Leaving out space complexity, including the recursion stack.
  • Calling an algorithm O(1) because it uses a hash map, ignoring the O(n) to build it.
  • Quoting average case when the question asks for worst case (quicksort, hash tables).
