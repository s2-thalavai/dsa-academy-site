Sorting

Sorting puts items in order. Eight classic algorithms show nearly every trade-off you'll be asked about: time, extra memory, stability and how they behave on nearly sorted data.

Technique 18 minute read

Picture it. Sorting a hand of cards. Most people use insertion sort: pick up one card at a time and slide it into place. Merge sort is two people each sorting half the deck and then interleaving their piles. Counting sort is dealing cards into 13 piles by rank and stacking the piles.

Two questions to ask about any sort

  • Time and space: how many comparisons or moves, and how much extra memory. Comparison sorts can't beat O(n log n) in the worst case, because there are n! possible orders and each comparison only halves the possibilities.
  • Stability: does it keep equal items in their original order? That matters when you sort records by one field after sorting by another, such as sorting orders by date and then by customer.

The simple O(n²) sorts

  • Bubble sort sweeps the array, swapping neighbours that are out of order. After pass k the k largest items are in place. Stop early if a pass makes no swaps.
  • Selection sort finds the smallest remaining item and swaps it into the next position. It always does O(n²) comparisons but only O(n) swaps.
  • Insertion sort grows a sorted prefix: take the next item and shift larger items right until its slot appears. On nearly sorted data each item moves only a little, so it's close to O(n). Real libraries switch to insertion sort for small pieces.

Merge sort

Merging two sorted lists takes one pass: repeatedly take the smaller front item. Merge sort is guaranteed O(n log n) and stable, but it needs O(n) extra space for the merge buffer. It's also the natural choice for linked lists (no random access needed) and for data too big for memory.

Quick sort

Pick a pivot, then partition: move everything smaller to its left and everything larger to its right. The pivot is now in its final place; sort the two sides recursively.

With good pivots each partition splits roughly in half, giving O(n log n). With bad pivots (always the smallest item) each split removes only one item, giving O(n²). A random pivot makes the bad case vanishingly unlikely. Quick sort runs in place and has excellent cache behaviour, which is why it's often the fastest in practice.

Heap sort

Build a max-heap in O(n), then repeatedly swap the root (the maximum) to the end of the array and sift the new root down. It's O(n log n) in every case and in place, but not stable and less cache-friendly than quick sort.

Counting and radix sort

When keys are integers in a small range 0..k, you don't need comparisons. Counting sort counts how many times each key appears, turns the counts into starting positions with a prefix sum, and places each item directly: O(n + k).

Radix sort sorts by one digit at a time, starting with the least significant, using a stable counting sort for each digit. Stability is what keeps earlier digit orders intact. For 32-bit integers in base 256 it takes 4 passes regardless of n.

When to use it

Reach for it when

  • Sorting first unlocks a simpler algorithm: two pointers, merging intervals, greedy choices, binary search.
  • Small or nearly sorted inputs: insertion sort beats the O(n log n) sorts there.
  • Integer keys in a small range: counting or radix sort beat comparison sorts.

Think twice when

  • You only need the top k items. A heap gives O(n log k).
  • You only need the k-th smallest. Quickselect is O(n) on average.

In your language

Notes for Java

  • Arrays.sort(int[]) uses dual-pivot quicksort: fast, not stable (stability doesn't matter for primitives).
  • Arrays.sort(Object[]) and Collections.sort use TimSort: stable, O(n log n), O(n) on sorted runs.
  • Sort with a comparator: Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0])). Comparators need boxed or object arrays, not int[].

Notes for JavaScript

  • arr.sort() with no comparator sorts as strings. Always pass (a, b) => a - b for numbers.
  • Since ES2019 sort must be stable, and V8 uses TimSort.
  • toSorted() (ES2023) returns a sorted copy and leaves the original alone.

Notes for TypeScript

  • Same runtime as JavaScript. Type comparators as (a: T, b: T) => number.

Notes for Python

  • sorted(xs) returns a new list; xs.sort() sorts in place. Both are TimSort: stable, O(n log n), O(n) on already-sorted runs.
  • Sort by key: sorted(people, key=lambda p: (p.age, p.name)). Because sorts are stable, you can also sort by the secondary key first and the primary key second.

Common mistakes

  • Sorting numbers in JavaScript without a comparator.
  • Writing return a - b comparators in Java for values that can overflow int.
  • Picking the first or last element as the quicksort pivot on sorted input, which hits the O(n²) worst case.
  • Assuming a sort is stable when the language doesn't promise it.
  • Sorting inside a loop when sorting once outside would do.
