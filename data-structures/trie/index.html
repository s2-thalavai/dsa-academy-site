Trie

A trie (prefix tree) stores strings character by character, so words with the same prefix share the same path. Looking up a word or a prefix takes time proportional to its length, no matter how many words are stored.

Data structureAdvanced 10 minute read

Picture it. A phone's contact search. Type "A" and the list narrows to names starting with A; type "An" and it narrows again. Each letter moves you one step down a tree of possibilities.

What a trie is

A trie is a tree where each edge stands for one character. The path from the root to a node spells a prefix. A node is flagged when that prefix is also a complete word.

The root is empty. To insert a word, start at the root and follow (or create) one child per character, then flag the last node. To search, follow the same path: if a child is missing, the word isn't there; if you reach the end, check the flag. A prefix search is the same walk without the final check.

How it sits in memory

Each node holds an array of child references (26 for lowercase English) and a boolean. The array makes child lookup O(1) but costs memory even for missing children. A hash map per node trades a little speed for much less memory when the alphabet is large, such as Unicode text.

Why not a hash set?

A hash set answers "is this exact word stored?" in O(L) too, since hashing reads every character. What it can't do cheaply is answer prefix questions: "which words start with ap?" would mean checking every word. In a trie it's one walk to the ap node.

Cost of each operation

OperationTimeWhy
Insert a word of length LO(L)One node per character, created if missing.
Search for a word or a prefixO(L)Follow one child pointer per character.
List all words with a prefixO(L + output size)Walk to the prefix node, then DFS below it.
Delete a wordO(L)Unmark the end and optionally prune empty nodes on the way back up.
SpaceO(total characters × alphabet)Each node has a slot per possible child. Hash-map children save space for big alphabets.

When to use it

Reach for it when

  • Autocomplete, spell check and prefix search.
  • Many queries of the form "does any word start with …?".
  • Word games on a grid (Boggle, Word Search II), where you prune paths that match no prefix.
  • Bitwise tries for maximum XOR problems (a trie over binary digits).

Think twice when

  • You only need exact-match lookups. A hash set is simpler and uses less memory.
  • The strings are long and share few prefixes, so most nodes have one child.

In your language

Notes for Java

  • Use TrieNode[] children = new TrieNode[26] for lowercase letters: fast and simple. Index with c - 'a'.
  • For larger alphabets use Map<Character, TrieNode>.

Notes for JavaScript

  • An object or Map per node works: children = new Map(). A fixed new Array(26) keeps children in alphabetical order without sorting.
  • Index with ch.charCodeAt(0) - 97.

Notes for TypeScript

  • children: (TrieNode | null)[] = new Array(26).fill(null) keeps the type honest about missing children.

Notes for Python

  • A compact trick is nested dicts: node = node.setdefault(ch, {}), with a special key such as "$" marking word ends.
  • A class with __slots__ = ("children", "end") uses less memory for big tries.

Code

Each node has 26 child slots, a flag for "a word ends here" and a count of words passing through, which makes "how many words start with this prefix?" an O(L) query.

Common mistakes

  • Forgetting the end-of-word flag, so prefixes like "app" are reported as words just because "apple" exists.
  • Allocating 26 children for every node when the alphabet is large or sparse, wasting memory.
  • Reusing a trie between test cases without clearing it.
