Hash tables

A hash table stores key–value pairs and finds any key in O(1) on average. It turns the key into an array index with a hash function, so lookups skip the search entirely.

Data structure 14 minute read

Picture it. A coat check. You hand over your coat and get ticket 47; the attendant hangs it on hook 47. To get it back you don't search every hook, you go straight to 47. If two coats get the same number, they share the hook, and the attendant checks the few coats hanging there.

What a hash table is

A hash table (also called a hash map, dictionary or associative array) stores key → value pairs. It answers "what's the value for this key?" without looking at other keys.

It works in three steps:

  1. A hash function turns the key into a large integer. The same key always gives the same number, and different keys usually give different numbers.
  2. The number is reduced to an index into an array of buckets, usually with hash % capacity.
  3. The bucket holds the entry. Because different keys can land in the same bucket, the bucket is checked for the exact key.

How it sits in memory

A good hash function spreads keys evenly, so each bucket holds about n / capacity entries. That ratio is the load factor. As long as it stays below a constant (Java uses 0.75), the expected chain is short, and insert, lookup and delete are O(1) on average.

Handling collisions

A collision is two different keys landing in the same bucket. With billions of possible keys and a few thousand buckets, collisions are guaranteed, so every hash table needs a strategy.

Separate chaining keeps a small list (or tree) of entries in each bucket, as in the diagram above. It's simple, and deletion is easy.

Open addressing stores entries directly in the array. On a collision it probes other slots until it finds a free one.

Open addressing uses less memory and is cache-friendly, but it needs a lower load factor (around 0.5 to 0.7) and careful deletion. Python's dict uses it; Java's HashMap uses chaining.

Load factor and resizing

When the load factor passes its limit, the table allocates an array twice as big and rehashes: every key goes into its new bucket, hash % newCapacity. A single resize is O(n), but as with dynamic arrays, doubling makes the average cost per insert O(1).

Hash sets

A hash set is a hash table with keys and no values. It answers "have I seen this?" in O(1) on average, which makes it the most common helper structure in interview solutions.

When to use it

Reach for it when

  • You need to know quickly whether you've seen something before: duplicates, visited sets, two-sum style complements.
  • You count things: frequencies of characters, words or numbers.
  • You group things by a key: anagrams by sorted letters, records by id.
  • You cache results (memoisation) or map ids to objects.

Think twice when

  • You need keys in sorted order, or the nearest key above or below a value. Use a balanced BST (TreeMap, sorted containers).
  • Keys are small dense integers. A plain array indexed by the key is faster and simpler.
  • Memory is very tight; empty buckets and per-entry overhead add up.

In your language

Notes for Java

  • HashMap<K, V> and HashSet<E> use chaining. When a bucket's chain passes 8 entries (and the table has at least 64 buckets) it turns into a red-black tree, so the worst case is O(log n).
  • The default load factor is 0.75 and capacity doubles on resize.
  • Keys must implement equals and hashCode consistently. Mutating a key after inserting it loses the entry.
  • getOrDefault, merge(key, 1, Integer::sum) and computeIfAbsent keep counting and grouping code short.
  • LinkedHashMap keeps insertion order (and can act as an LRU cache); TreeMap keeps keys sorted.

Notes for JavaScript

  • Use Map and Set for hash tables. They accept any key type, keep insertion order and have a size property.
  • Plain objects only take string or symbol keys: obj[1] and obj["1"] are the same entry. They also inherit keys like toString, so prefer Map.
  • Object keys in a Map are compared by reference, not by contents. To key by a pair, build a string such as `${r},${c}`.

Notes for TypeScript

  • Map<string, number> and Set<number> type the keys and values. map.get(k) returns V | undefined, so handle the missing case: map.get(k) ?? 0.
  • Record<string, number> types a plain object used as a dictionary.

Notes for Python

  • dict and set use open addressing. Since Python 3.7, dict keeps insertion order.
  • Keys must be hashable: int, str and tuple work, list and dict don't. Use a tuple such as (r, c) as a grid key.
  • collections.Counter counts in one line; collections.defaultdict(list) groups without checking for missing keys.
  • String hashes are randomised per process (PYTHONHASHSEED), so never rely on the iteration order of a set of strings.

Code

Keys are strings hashed with a polynomial hash (h = h × 31 + char, kept small with a modulus). Each bucket is a list of entries. When the load factor passes 0.75, the bucket array doubles and every key is rehashed.

Common mistakes

  • Assuming the map is sorted, or that iteration order is stable across runs or languages.
  • Using mutable objects (lists, arrays, objects with changing fields) as keys.
  • Overriding equals without hashCode in Java, so equal keys land in different buckets.
  • Forgetting that lookups are O(1) only on average. Adversarial or badly distributed keys can degrade a weak hash.
  • Checking if (map.get(k)) in JavaScript, which treats a stored 0 as missing. Use map.has(k).
