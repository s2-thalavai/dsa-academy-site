Merge intervals

Sort intervals by their start, then walk through them once. Each interval either overlaps the one you're building, so you extend it, or starts after it ends, so you close it and start a new one.

Coding pattern

Picture it. Booking a meeting room. Lay all requests on a timeline in start order. Any meeting that starts before the current one finishes needs the room at the same time; you merge or count them as you sweep left to right.

Recognise it

  • The input is a list of [start, end] pairs: meetings, bookings, ranges, segments.
  • The question asks to merge overlaps, insert a new interval, find gaps or intersections, or count how many overlap at once.
  • A brute force compares every pair of intervals.

The template

sort intervals by start
merged = [first interval]
for each next interval [s, e]:
    last = merged's final interval
    if s <= last.end: last.end = max(last.end, e)    ← overlap: extend
    else:             append [s, e]                  ← gap: start a new one

How it works

After sorting by start, only the most recent merged interval can overlap the next one: everything earlier ends even sooner. That's why one pass is enough.

Two variations come up constantly:

  • Insert a new interval into a sorted, non-overlapping list: copy everything that ends before it, merge everything that overlaps it, copy the rest.
  • Count overlaps (minimum meeting rooms): sort the starts and the ends separately and sweep. Each start before the next end needs another room.

Cost of each operation

OperationTimeWhy
Merge overlapping intervalsO(n log n) time, O(n) outputThe sort dominates; the sweep is O(n).
Insert into a sorted listO(n)Already sorted: one pass.
Intersections of two sorted listsO(n + m)Two pointers: advance whichever interval ends first.
Minimum roomsO(n log n)Sort starts and ends, then sweep both arrays together.

Code

Every function treats intervals as closed: [1, 4] and [4, 5] touch and overlap.

Common mistakes

  • Forgetting to sort first, or sorting by end when the merge logic expects start order.
  • Using < instead of <= when touching intervals like [1,4] and [4,5] should merge (check the problem statement).
  • Setting last.end = e instead of max(last.end, e), which shrinks the merged interval when a short one sits inside a long one.
  • Mutating the input intervals while sorting or merging when the caller still needs them.
