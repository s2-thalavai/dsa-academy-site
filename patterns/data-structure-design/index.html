Data structure design

Design questions ask you to build a class whose operations all meet a time limit, usually O(1). The answer is almost always two simple structures combined so that each covers the other's weak spot.

Coding pattern

Picture it. A library with both a card catalogue and a returns trolley. The catalogue finds any book instantly but knows nothing about order; the trolley knows exactly which book came back most recently but can't find anything. Together they answer both kinds of question quickly.

Recognise it

  • "Design a class" with a list of operations and a required complexity for each.
  • O(1) lookup and O(1) ordering (LRU, LFU).
  • O(1) insert, delete and random choice (randomised set).
  • A stack or queue that also reports its minimum, or a queue built from stacks.

The template

list each operation and its required cost
for each one, pick the structure that already does it in that time:
    lookup by key → hash map
    order by recency / insertion → doubly linked list (with sentinels)
    random access / random choice → dynamic array
    min or max so far → a second stack, or a heap
keep the structures in sync inside every method

How it works

  • LRU cache: a hash map from key to list node gives O(1) lookup; a doubly linked list ordered by recency gives O(1) move-to-front and O(1) eviction. Sentinel head and tail nodes remove every edge case.
  • Min stack: push each value together with the minimum so far. The current minimum is always on top.
  • Queue from two stacks: push onto an in stack; when you need the front, pour in into an out stack if out is empty. Each element moves once, so operations are amortised O(1).
  • Randomised set: an array holds the values (random choice is a random index) and a map holds each value's index. To delete, swap the value with the last element, update that element's index, then pop.

Cost of each operation

OperationTimeWhy
LRU cache get / putO(1)Hash map lookup plus a constant number of pointer changes.

Code

The LRU cache is built by hand from a hash map and a doubly linked list with sentinels, rather than with LinkedHashMap or OrderedDict, because that's what interviewers ask for. getRandom is only called when one value is left, so the output is the same every run.

Common mistakes

  • Forgetting to update the hash map when a node is evicted or moved.
  • Using a singly linked list for LRU, so removing a node in the middle is O(n).
  • In the randomised set, removing the last element and then trying to update its (now removed) index.
  • In the two-stack queue, pouring into out while it still has elements, which breaks the order.
